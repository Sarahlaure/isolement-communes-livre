3  Le code

Le projet est organisé en modules Python, rangés dans le dossier src/. Chaque module fait une seule chose et peut être testé séparément. Le notebook rapport.ipynb les appelle dans l’ordre et raconte l’analyse. Ce chapitre explique ce que fait chaque module, ses fonctions principales et les choix que nous y avons faits. Les extraits de code sont repliés : il suffit de cliquer sur « Voir le code » pour les afficher.

1 Vue d’ensemble

Les modules s’enchaînent comme le montre la figure 1. Chaque flèche correspond à un fichier : les données brutes sont téléchargées dans data/raw/, nettoyées dans data/interim/, puis les tableaux finaux sont écrits dans data/processed/.

Un principe commun : les fonctions qui font les calculs travaillent sur de simples tableaux pandas, sans dépendre des cartes ni des fichiers. Cela permet de les tester avec de petits jeux de données fictifs.

2 download : télécharger les données

Rôle. Ce script est la mémoire écrite de la provenance de nos données. Au lieu de télécharger les fichiers à la main, avec des clics qu’on ne peut pas rejouer, nous les téléchargeons par du code, ce qui rend le projet reproductible.

Où vont les fichiers. Le chemin du dossier data/raw/ est construit à partir de l’emplacement du script lui-même (Path(__file__).resolve().parents[1]), c’est-à-dire la racine du projet. Le chemin est donc juste quel que soit l’ordinateur ou le dossier d’où on lance le script.

Ce qu’il contient.

  • Un dictionnaire FICHIERS_AUTO décrit les cinq fichiers téléchargés automatiquement : pour chacun, l’adresse, ce que c’est et à quoi il sert.
  • Un dictionnaire FICHIERS_MANUELS décrit les trois fichiers à placer à la main (population, contours, revenus), avec où les trouver.
  • telecharger(url, destination) télécharge un fichier.
  • verifier(destination) contrôle qu’il est valide.
  • main() enchaîne le tout et renvoie 0 si tout s’est bien passé.

Les choix. Trois précautions rendent le téléchargement fiable.

  1. Si le fichier existe déjà, il n’est pas retéléchargé : on peut relancer le script sans risque.
  2. Le fichier est d’abord écrit sous un nom temporaire (.part) et renommé seulement à la fin. Si la connexion coupe en route, on ne garde pas un fichier tronqué qu’on prendrait ensuite pour un fichier complet.
  3. Le fichier est lu par blocs de 1 Mo (stream=True), sans tout charger en mémoire, ce qui est utile pour un fichier de 163 Mo.

Enfin, verifier contrôle que le fichier est bien ce qu’il prétend être : un site peut répondre « succès » mais renvoyer une page web à la place du fichier. Un fichier parquet commence toujours par les quatre octets PAR1, et un CSV ne doit pas commencer par < (début d’une page HTML).

Voir le code de la fonction telecharger 
def telecharger(url: str, destination: Path, taille_bloc: int = 1 << 20) -> None:
    if destination.exists() and destination.stat().st_size > 0:
        print(f"  déjà présent : {destination.name}")
        return

    temporaire = destination.with_suffix(destination.suffix + ".part")
    with requests.get(url, stream=True, timeout=120,
                      headers={"User-Agent": "projet-ensae-python"}) as reponse:
        reponse.raise_for_status()   # lève une erreur si le serveur répond 403, 404, 500...
        with open(temporaire, "wb") as fichier:
            for bloc in reponse.iter_content(chunk_size=taille_bloc):
                fichier.write(bloc)

    temporaire.rename(destination)   # le fichier est complet : on lui donne son vrai nom

3 inspect_bpe et prepare_bpe : préparer la BPE

inspect_bpe.py. Avant d’écrire le moindre calcul, ce script inspecte la BPE avec DuckDB : il affiche les colonnes réelles du fichier, le nombre de lignes, le nombre d’équipements de chaque type du panier, et signale les codes du panier absents du fichier. Il nous a permis de vérifier que nos 33 codes TYPEQU existent bien dans la BPE 2025 avant de construire le reste.

prepare_bpe.py. Ce script extrait de la BPE uniquement ce dont le projet a besoin et écrit data/interim/equipements.parquet.

  • Le dictionnaire SERVICES est le cœur du module : il associe à chaque service les codes TYPEQU qui comptent pour lui. C’est le seul endroit où le panier est défini. Pour l’ajuster, on ne modifie que ce dictionnaire.
  • table_de_correspondance() transforme ce dictionnaire en tableau (TYPEQU, service), une ligne par code. Elle vérifie au passage qu’un code n’appartient pas à deux services à la fois.
  • preparer() lit la BPE avec DuckDB et écrit le fichier propre.
  • resume() produit un tableau de contrôle par service : nombre d’équipements, nombre avec coordonnées, nombre de communes concernées.

Les choix. DuckDB lit directement le fichier parquet avec une requête SQL, sans charger les 95 colonnes en mémoire. Le filtre se fait par une jointure interne (INNER JOIN) avec le tableau de correspondance : on ne garde que les types du panier. Les coordonnées sont converties en nombres avec TRY_CAST, qui donne une valeur vide au lieu de planter si la case est vide. Enfin, les équipements sans coordonnées sont conservés : ils servent à la présence.

Voir le code de la requête 
requete = f"""
    SELECT
        b.DEPCOM                        AS depcom,
        c.service                       AS service,
        b.TYPEQU                        AS typequ,
        TRY_CAST(b.LAMBERT_X AS DOUBLE) AS x,
        TRY_CAST(b.LAMBERT_Y AS DOUBLE) AS y,
        b.QUALITE_XY                    AS qualite_xy
    FROM read_parquet('{bpe.as_posix()}') AS b
    INNER JOIN correspondance AS c ON b.TYPEQU = c.TYPEQU
    WHERE CAST(b.EPSG AS VARCHAR) = '2154'
"""
equipements = con.sql(requete).df()

4 communes : la table des communes

Rôle. Ce module construit la table de base, une ligne par commune ou arrondissement, avec son centre, sa surface et sa population. Il distingue deux niveaux de fonctions : celles qui lisent les cartes (avec geopandas) et celles qui travaillent sur de simples tableaux pandas, faciles à tester.

Les choix.

  • choisir_colonne existe parce que les noms de colonnes changent d’une édition à l’autre (le code s’appelle code_insee chez nous, mais insee_com ou codgeo ailleurs). La fonction essaie plusieurs noms et renvoie une erreur claire si aucun ne convient.
  • geometrie_vers_table calcule le centre de chaque commune avec geometry.centroid et sa surface avec geometry.area / 1e6 (les unités sont des mètres, on divise par un million pour passer en km²).
  • assembler_base retire les trois villes mères (Paris, Lyon, Marseille), dont les codes sont repérés automatiquement comme les valeurs de la colonne parent des arrondissements, ajoute les arrondissements, retire les codes qui commencent par 97 ou 98, puis fait deux contrôles : tous les codes ont cinq caractères, et aucun n’est en double.
  • fusionner_population fait une jointure à gauche (how="left") : aucune commune ne disparaît. Elle remet les codes sur cinq caractères avec zfill(5), et elle renvoie un journal qui compte les communes sans population et les codes du fichier absents de la base.
Voir le code de assembler_base 
def assembler_base(communes: pd.DataFrame, arrondissements: pd.DataFrame) -> pd.DataFrame:
    villes_meres = set(arrondissements["parent"])
    sans_villes = communes[~communes["code"].isin(villes_meres)]
    base = pd.concat(
        [sans_villes.drop(columns=["parent"], errors="ignore"),
         arrondissements.drop(columns=["parent"], errors="ignore")],
        ignore_index=True,
    )
    base = base[~base["code"].str.startswith(PREFIXES_HORS_METROPOLE)].copy()
    if (base["code"].str.len() != 5).any():
        raise ValueError("Des codes commune ne font pas 5 caractères.")
    doublons = base["code"].duplicated(keep=False)
    if doublons.any():
        raise ValueError(f"Codes en double : {sorted(base.loc[doublons, 'code'].unique())[:10]}")
    base["densite"] = base["population"] / base["surface_km2"]
    return base.sort_values("code").reset_index(drop=True)

5 distances : présence et distances

Rôle. Ce module applique la règle du chapitre 1 : il dit, pour chaque commune et chaque service, si le service est présent, et à quelle distance se trouve le plus proche.

distance_to_nearest. Elle construit un arbre cKDTree avec les positions des équipements et l’interroge avec les centres des communes (query(..., k=1) renvoie la distance au plus proche voisin). Les équipements dont les coordonnées sont vides (NaN) sont d’abord retirés. S’il n’y en a plus aucun, elle renvoie des valeurs vides.

presence_par_service. Elle crée un tableau de zéros (False) de la taille commune × service, puis met True aux couples (commune, service) qui existent dans la BPE. Pour éviter une boucle lente sur 500 000 équipements, elle utilise get_indexer, qui renvoie la position de chaque code dans l’index (et −1 s’il est absent), puis remplit le tableau en une seule opération.

distances_par_service. Pour chaque service, elle calcule la distance de toutes les communes à l’équipement le plus proche, convertit en kilomètres, puis met 0 là où le service est présent. Deux options permettent de réaliser les variantes de robustesse :

  • regle_presence=False ne met jamais 0 : la distance est toujours celle du centre de la commune à l’équipement le plus proche ;
  • qualites=["A", "B"] ne garde, pour le calcul de distance, que les équipements dont la position est de bonne qualité. La présence n’est pas filtrée.
Voir le code de distances_par_service 
def distances_par_service(communes, equipements, services, qualites=None, regle_presence=True):
    origines = communes[["x", "y"]].to_numpy(dtype=float)
    presence = presence_par_service(communes["code"].to_numpy(), equipements, services)
    colonnes = {}
    for service in services:
        localises = equipements[equipements["service"] == service].dropna(subset=["x", "y"])
        if qualites is not None:
            localises = localises[localises["qualite_xy"].isin(qualites)]
        d_km = distance_to_nearest(origines, localises[["x", "y"]].to_numpy(dtype=float)) / 1000.0
        if regle_presence:
            d_km = np.where(presence[service].to_numpy(), 0.0, d_km)
        colonnes[service] = d_km
    distances = pd.DataFrame(colonnes, index=pd.Index(communes["code"].to_numpy(), name="code"))
    return distances, presence

6 indice : de 19 distances à un indice

Rôle. Ce module met en code les trois étapes de la section L’indice d’isolement.

Les choix.

  • np.log1p(d) calcule directement \(\ln(1+d)\) et reste précis pour de petites valeurs de \(d\).
  • standardiser utilise un écart-type avec ddof=0 (division par \(n\), pas par \(n-1\)) : nous standardisons toute la population des communes, pas un échantillon. Si un service avait un écart-type nul (même valeur partout), la colonne devient une colonne de zéros au lieu de provoquer une division par zéro.
  • Les services « vitaux » et les thèmes sont des dictionnaires définis en haut du module (SERVICES_VITAUX, THEMES), ce qui les rend faciles à modifier. Pour poids_themes_equilibres, le poids d’un service est \(1/n\), où \(n\) est le nombre de services de son thème, calculé avec value_counts.
  • indice_pondere vérifie qu’aucun poids ne manque, calcule le numérateur \(\sum w z\) par ligne et divise par \(\sum w\).
  • indice_acp utilise PCA(n_components=1) de scikit-learn (Pedregosa et al. 2011). Le signe d’une composante principale est arbitraire : la fonction compare le score à un indice de référence et change le signe si la corrélation est négative, pour qu’un score élevé veuille toujours dire « plus isolé ». Elle renvoie aussi la part de variance expliquée.
Voir le code de standardiser, indice_pondere et indice_acp 
def standardiser(tableau: pd.DataFrame) -> pd.DataFrame:
    moyenne = tableau.mean()
    ecart = tableau.std(ddof=0).replace(0, np.nan)
    return ((tableau - moyenne) / ecart).fillna(0.0)


def indice_pondere(z: pd.DataFrame, poids: dict[str, float]) -> pd.Series:
    w = pd.Series(poids).reindex(z.columns)
    if w.isna().any():
        raise ValueError(f"Poids manquants pour : {list(w[w.isna()].index)}")
    numerateur = (z * w).sum(axis=1)
    denominateur = float(w.sum())
    return (numerateur / denominateur).rename("indice")


def indice_acp(z: pd.DataFrame, reference: pd.Series) -> tuple[pd.Series, float]:
    acp = PCA(n_components=1, random_state=0)
    scores = pd.Series(acp.fit_transform(z.to_numpy())[:, 0], index=z.index, name="indice_acp")
    if np.corrcoef(scores.to_numpy(), reference.to_numpy())[0, 1] < 0:
        scores = -scores
    return scores, float(acp.explained_variance_ratio_[0])

7 descriptif : statistiques descriptives

Rôle. Ce module regroupe les calculs des statistiques descriptives du chapitre 3.

  • resume_par_service(distances_km) calcule, pour chaque service, la part de communes équipées (la part des distances égales à 0), la médiane, la moyenne, le 90ᵉ et le 99ᵉ centile et le maximum.
  • part_population_eloignee(distances_km, population, seuils_km) calcule, pour chaque service et chaque seuil, la part de la population qui vit dans une commune plus éloignée que le seuil. Pour chaque seuil, la fonction construit un tableau de booléens distance > seuil, le multiplie par la population de chaque commune, puis divise la somme par la population totale :

\[\text{part}_k(t) = \frac{\sum_c \text{pop}_c \cdot \mathbf{1}\{d_{c,k} > t\}}{\sum_c \text{pop}_c}\]

  • communes_les_plus_isolees(base, indice, n) liste les \(n\) communes à l’indice le plus élevé, avec leur nom, leur population et leur surface.
  • decrire_indice(indice) renvoie les quantiles de l’indice (1 %, 10 %, 25 %, 50 %, 75 %, 90 %, 99 %).

Une commune équipée a une distance de 0, donc elle n’est jamais comptée comme éloignée, quel que soit le seuil. Les communes sans population renseignée sont écartées du calcul.

8 analyse : revenu, tests et typologie

Rôle. Ce module regroupe les analyses de la seconde partie du projet.

lire_revenu. Le fichier Filosofi est en format long : une ligne par couple (territoire, indicateur). La fonction teste plusieurs encodages et séparateurs pour être tolérante avec le format du fichier, puis ne garde que les lignes dont le type de territoire est une commune (COM) ou un arrondissement (ARM) et dont l’indicateur est MED_SL. Les valeurs absentes (secret statistique s, donnée manquante vm) deviennent des cases vides avec pd.to_numeric(..., errors="coerce").

correlation_spearman. Elle ne garde que les paires où les deux valeurs sont renseignées, puis appelle scipy.stats.spearmanr (Virtanen et al. 2020). Elle renvoie ρ, la p-value et le nombre de paires.

comparer_groupes. Elle appelle scipy.stats.kruskal sur les valeurs de chaque groupe et calcule la taille d’effet \(\varepsilon^2 = H/(n-1)\). Elle renvoie aussi un tableau par groupe (effectif, médiane, premier et troisième quartiles).

choisir_k et typologie. Elles utilisent KMeans de scikit-learn. choisir_k calcule la silhouette sur un échantillon de 5 000 communes, car elle est coûteuse sur 34 788 points. typologie lance le k-means (avec n_init=10, c’est-à-dire dix initialisations aléatoires dont la meilleure est gardée) et renumérote les groupes du mieux desservi (0) au moins bien desservi, d’après la moyenne de leurs \(z\). Sans cette étape, la numérotation brute du k-means serait aléatoire. La fonction calcule aussi le plan des deux premières composantes principales pour dessiner les groupes, et les profils moyens de chaque groupe.

Voir le code de correlation_spearman et comparer_groupes 
def correlation_spearman(x: pd.Series, y: pd.Series) -> dict:
    paires = pd.concat([x, y], axis=1, keys=["x", "y"]).dropna()
    rho, p = stats.spearmanr(paires["x"], paires["y"])
    return {"rho": float(rho), "p_value": float(p), "n": int(len(paires))}


def comparer_groupes(valeur: pd.Series, groupe: pd.Series) -> tuple[dict, pd.DataFrame]:
    d = pd.concat([valeur, groupe], axis=1, keys=["v", "g"]).dropna()
    listes = [s["v"].to_numpy() for _, s in d.groupby("g", observed=True)]
    h, p = stats.kruskal(*listes)
    n = len(d)
    resultat = {"H": float(h), "p_value": float(p), "n": int(n), "epsilon2": float(h / (n - 1))}
    tableau = d.groupby("g", observed=True)["v"].agg(
        communes="size", mediane="median", q25=lambda s: s.quantile(.25), q75=lambda s: s.quantile(.75))
    return resultat, tableau.round(3)

9 Les tests

Le dossier tests/ contient des tests automatiques, lancés avec pytest. Ils vérifient que les fonctions font bien ce qu’on attend sur de très petits jeux de données fictifs, où l’on peut calculer le résultat à la main.

Un test illustre bien l’intérêt de cette démarche. Dans test_distances_regle_principale, trois communes A, B et C sont placées sur des coordonnées simples. On calcule à la main que la distance de C à la pharmacie la plus proche est \(\sqrt{10\,000^2 + 20\,000^2}/1\,000\) km, et on vérifie que le code donne bien ce résultat. Si quelqu’un modifie le code et casse la règle de distance, le test échoue immédiatement. Le dernier test est un test de bout en bout : on fabrique une petite France fictive avec un hameau placé très loin de tout, et on vérifie que l’indice le repère comme la commune la plus isolée.
